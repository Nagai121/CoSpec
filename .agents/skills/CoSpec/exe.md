# Exe

ExeはDiscussionとMemoryの状態を、コード変更、ファイル操作、コマンド実行その他の実世界の操作へ射影する軸である。入力全体または入力の文末に独立して置かれた明示的な`exe`だけで起動する。

## Execution faults

Exeにおける主要なexecution faultを次の4つとする。

1. シークレットの流出: secretsまたは疑わしい値を、出力、Memory、Git、外部送信その他の経路へ漏らすこと。
2. オーバーエンジニアリング: 一般目的を満たすために必要な範囲を超えて、構造、機能、依存関係、抽象化、変更を追加すること。
3. リワードハッキング: 一般性を満たさず、サンプル、テスト、閾値、seed、観測指標だけを攻略すること。
4. 要求仕様の無視: 承認された目的、Specification、成果物、制約、境界または停止条件を省略、置換、縮小、逸脱すること。

シークレットの流出と要求仕様の無視は、Exe前の制約読込みと既存の承認・安全境界で抑制する。オーバーエンジニアリングとリワードハッキングは、実装選択時の「一般→最小選抜」で抑制する。

## Preconditions

- 実際の変更を開始する前に、`SKILL.md`のSafety、current Specification、承認されたDiscussion差分、および対象操作に必要な制御文書を読み、同時に適用する。Git操作では`Git.md`も適用する。
- 承認された目的、成果物、対象範囲、制約、非対象、および停止条件を実行契約から識別する。これらを別の評価指標、サンプル、テスト、またはAI独自の目的へ置換しない。
- secretsの入力元、出力先、保存先、外部送信境界を必要範囲で確認し、実値を出力またはMemoryへ取り込まない。
- Memory内current Specificationが存在する場合は、常に基準仕様として参照する。
- 直前のDiscussionで人間が明示的に決定した内容は、その実行に限る一時差分として基準仕様へ重ねられる。
- 人間が入力全体として`exe`を置いた時点で、直前のDiscussionに含まれる明示的な一時差分の実装を承認したものと扱う。
- 人間が入力の文末に独立した`exe`を置いた場合は、同じ入力内でそれより前に書かれた指示を実装承認の対象とする。
- 一時差分が基準仕様と矛盾する場合は、直前かつ明示的な人間の決定を今回の実行に限って優先する。
- current Specificationが存在しない場合は、直前のDiscussionを一時的な実行契約として使用できる。
- Discussionを一時差分または実行契約に使用する場合、実行対象、必要な環境、依存関係、入出力、処理境界、成果物、停止条件が必要範囲で人間により明示され、追加の仕様判断なく実行できることを確認する。
- 仕様の根幹変更とは、ファイルの消去、またはシステムアーキテクチャもしくは処理フローの白紙化をいう。
- 仕様の根幹変更またはその他の破壊的操作は、対象と影響が人間に示され、明示的に承認されている場合に限り実行できる。承認がなければ実行前に停止する。
- 曖昧な差分、未確定事項、仕様不足、参照不能、重大リスク、secrets混入リスクがあれば実行前に停止する。

## General-to-minimal selection

実装を選ぶときは、承認された目的を縮小せず、必ず一般性を先に評価し、その後に最小性を評価する。

1. 承認された目的、Specification、および今回限りのDiscussion差分から、目的と許可された一般化範囲を確定する。
2. 目的を一般的に満たし得る実装候補を必要範囲で考える。候補の検討を人間向けに機械的に列挙する必要はない。
3. 各候補が、承認された対象フィールド、入力範囲、成果物および条件に対して一般性を満たすか判定し、満たさない候補を除外する。
4. 一般性を満たす候補の中から、承認された目的の達成に不要な実装を含まない最小の候補を選ぶ。
5. 選ばれた候補だけを実行する。

### Generality filter

- サンプル、テスト、閾値、seed、評価値その他の観測条件を、より一般的な最終目的へ置換しない。これらはSpecificationが明示的に目的そのものと定めない限り、目的の成立を検証する条件として扱う。
- 特定サンプル、特定入力、特定seed、単発の閾値超過、既知テストだけに特殊化した候補は、元の目的がより一般的な成立を要求する場合、一般性を満たさない。
- サンプル固有性を実装理由にしない。対象フィールド一般に成立する実装を優先し、サンプルでその成立を検証する。
- Specificationが対象を特定サンプルまたは限定範囲へ明示的に限定している場合、その範囲をAI判断で一般化しない。一般化は承認された目的とSpecificationから導ける範囲に限る。
- 一般性フィルタにより、観測指標だけを攻略するリワードハッキングを除外する。

### Minimal selection

- 判断基準を「これがなければ、承認された目的を一般的に満たせないか」とする。満たせるなら追加しない。
- 将来便利そう、拡張しやすそう、一般的なbest practice、より綺麗なarchitecture、念のため、将来使う可能性、周辺整理、追加抽象化の可能性を、それ単独で追加実装の理由にしない。
- 承認された目的に不要なrefactor、abstraction、dependency、feature、configuration、artifact、future-proofingを追加しない。
- 最小化するのはAIが目的達成手段として追加する実装であり、人間が確定した目的、成果物、Specificationではない。
- 目的自体が大規模なら、それを一般的に満たすために必要な大規模実装を行える。規模だけを理由に要求仕様を縮小しない。
- 最小選抜により、一般目的に不要な追加を行うオーバーエンジニアリングを除外する。

## Execution

- Git操作を実行する場合は、`SKILL.md`で定義された`Git.md`の追加契約を適用する。
- 「一般→最小選抜」で選ばれた実装だけを実行する。最小性を一般性より先に評価しない。
- 基準仕様と承認された一時差分を合成した実行契約の範囲だけを実行する。
- Discussionを一時差分または実行契約に使用しても、その内容をSpecificationへ自動保存しない。永続化はUpdateでのみ行う。
- 未承認の依存関係、構造、処理、成果物形式を追加しない。
- 実行途中でエラー、追加判断、仕様不足、secrets混入疑いが生じた場合は停止する。
- 停止原因と必要な追加判断をDiscussionへ戻す。
- 実行結果、停止、完了をMemoによりLogへ自動保存する。
- 実行後、変更が選択した実行契約内に収まり、secretsまたは疑わしいファイルが混入していないことを確認する。

## State

- `true`: 選択した実行契約の範囲で完了した。
- `halfway`: 一部実行後に停止した。
- `blocked`: 実行前に停止した。
